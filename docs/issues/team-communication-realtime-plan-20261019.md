# 实时沟通：已核实事实与最小增量

2026-10-19；本轮只读代码核查，没有改生产实时通道、请求通知权限、注册设备订阅或生成正式推送密钥。iOS系统/Home Screen官方条件由父任务并行核实；安卓和实体手机均未实测。

## 先给结论

目前聊天是“前台定时拉取”，不是即时事件聊天。已有 PWA 和 Web Push 底座，但班次/卫生/培训/审批提醒与团队聊天是两条尚未连接的链路；员工发消息也不会自动触发后台 MiniMax，主对话 Dot 没有事件接收。因此只开通 MiniMax 账号，不能让主对话持续即时看到店内消息。

## 当前真实实现

| 环节 | 核实结果 | 实际含义 |
|---|---|---|
| 前台选中聊天 | shared/TeamCommunication.tsx 每3秒pull；列表每5秒reload；两者仅 document.visibilityState=visible 时执行 | 活跃页通常等下一轮再请求，且有网络/后端耗时；不是实时送达承诺 |
| 消息呈现 | pull 依次等待消息、纪要、任务三个请求后才 setMessages | 纪要/任务慢会拖住聊天显示；可拆开处理，避免把元数据延迟传给消息 |
| 后台/锁屏 | 隐藏时停止上述pull；outbox虽另有5秒定时器，手机浏览器可挂起/节流 | 页面后台时不能靠3秒轮询持续收发，需系统推送与恢复补拉 |
| 断网恢复 | online事件reload并改变refreshKey，重启当前频道拉取；按after cursor分页，hasMore立即续页；seq去重 | 能补拉但当前重启cursor=0、清空内存列表，长历史可拖慢恢复；没有专门visibilitychange/focus即刻补拉 |
| 离线发件 | IndexedDB youme-team-outbox-v1，按账号/门店scope保存文字及附件，requestId幂等，5秒尝试，失败指数退避至60秒 | 响应丢失不重复建消息；仍要等待浏览器进程恢复、网络及权限有效；任务动作不是离线outbox |
| Service Worker/PWA | main.tsx注册employee-sw.js；manifest含id/start_url/scope= /、display=standalone、图标；SW缓存外壳并处理push和notificationclick | 底座存在，不代表设备已经获准通知或推送已投递 |
| 通知订阅 | PushSettings检测PushManager/Notification，用户点启用才requestPermission，随后取/my/push-key并保存/my/subscription | 不应替用户自动授权。push-key接口可能生成VAPID，故本轮没有调用该接口 |
| 已有推送 | EmployeeReminderService收集班次、卫生任务、培训及审批/换班事件，1分钟worker；VAPID、订阅、租约、重试、404/410失效处理已存在 | 可复用底座；未接团队消息和运营计划，现有分钟扫描也不适合作为即时聊天唯一触发 |
| 推送正文 | SW只显示通知标题和通用“打开应用查看详情”，点击回应用 | 可保留这项隐私边界，不把私聊正文或附件放锁屏通知 |
| 未读/已读 | unread=lastSeq与成员可见下限/已读seq之差；选中频道页面可见且pull成功就PUT/read | 是页面拉取位置，不证明员工看懂内容；不是设备送达ACK，更不是接收任务或完成 |
| 发送/送达 | outbox收到API成功后移除；无每个收件设备已接收字段 | API成功仅证明服务端落库。推送服务接收也不等于手机展示或人已读 |
| 提醒终态 | 主reminder记录在所有设备成功或重试耗尽后都可能写status=sent；单设备delivery另有sent/failed/attempts | 不能拿主记录sent当员工已收到；复用前应区分服务商已接受、失败耗尽和人已读 |
| WebSocket | 项目已有Socket.IO和emitToStaff，但shared聊天无socket/EventSource订阅，TeamCommunication/Operations未发聊天事件 | 可复用传输，不应另造聊天或向整个store广播私聊信息 |
| MiniMax / Dot | AI只有管理员手动generate/lookup/publish；消息send未入AI队列；Dot只靠人工导入导出 | 当前双方发消息都不会自动唤醒主对话，也不存在24小时自动值守 |

## 下一批建议最小范围（本轮未实现）

1. **前台先到、恢复不漏**：消息成功落库后向当前获准成员的现有staff socket发最小变更事件（channelId/lastSeq，不带正文）；前台立即按seq补拉，保留3秒轮询兜底。复用existing emitToStaff，但发送前验证门店、活动成员和会话，移除成员后立即停止；禁止broadcastToStore私聊事件。消息先显示，纪要/任务并行更新；visibilitychange/focus/online立刻恢复补拉，保留当前已加载cursor及已核实消息，账号/门店切换清除。
2. **后台有提醒**：复用现有订阅与发送服务，增加“团队新消息/任务状态变化”的持久事件队列及幂等消费，按当前成员复核、合并同频道短时间通知、静默时段、过期/已读取消、跨设备去重。不能只等1分钟通用worker。通知只带通用提示与受保护深链，点击后重新鉴权拉原文。iOS/Android按真实安装方式、权限、后台、锁屏分别验收，不承诺系统一定即时展示。
3. **明确状态**：界面分“本机待发、服务器已保存、设备已取到、已读位置、任务已确认接收”；确需设备ACK再增加经鉴权的游标确认。提醒日志分provider accepted/exhausted，不把重试耗尽叫送达；员工“收到任务”仍为本人动作。
4. **AI及时响应另设边界**：只有指定试点频道和明确@AI/任务触发才进服务端持久队列；消息id+规则版本幂等，回应前重验成员/计划版本，失败和超时可见且不盲重试。先生成私有草稿给审批人；自动发员工、费用/频次、工作时段和人工接管需具体授权。先解决中国区订阅/模型/用途与凭据目标问题，不把通知推送当作模型触发。
5. **Dot事件连接单独确认**：若用户希望主对话参与持续管理，需要受控连接、最小事件范围、接收端与审计/停用机制；当前没有该连接。未获授权前保持管理员回传，不能用MiniMax已配置替代Dot已接入。

## 可验收门槛

前台双设备目标先按同网络p95≤2秒设计并实测；断网恢复后自动补拉、无丢失或重复；后台/锁屏分别记录推送服务接收、系统展示和点击打开，失败提供站内未读及人工升级。两台设备同账号、成员被移除、退出登录/换账号、通知拒绝、订阅失效410、弱网、进程被系统终止、长历史恢复、重复事件/推送、AI队列超时均需验证。现阶段这些是目标用例，不是已达到的SLA。

先做1—3可改善人与人的沟通，不依赖模型账号、WhatsApp或Dot连接；4—5涉及付费外发与持续权限，须先明确边界。无需替换现有聊天、任务、附件或PWA系统。
