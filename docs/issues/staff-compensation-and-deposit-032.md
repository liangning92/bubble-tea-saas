# 员工奖惩入口与押金工资联动（2026-10-08）

用户发现已关联的首月押金没有进入待发工资。线上只读汇总确认一条待发工资缺少押金扣除计划；原表单必须点击自动计算才能带入押金，列表没有编辑入口。另按用户要求，将现金金额的员工奖励/处罚与积分调整区分，提供独立员工管理入口。

- “员工管理 → 奖惩”独立页面：员工、所属月份、奖励/处罚、Rp 整数金额、原因；管理员创建/撤销，店长读取，员工不能查看其他员工。保存时保留 UUID、作者、日期及撤销记录，重复提交不重复计入。
- 工资已存在且待发时，添加/撤销奖惩与工资金额在同一事务中更新，保留其他奖金及扣款。工资尚未创建时先保存记录，创建工资自动带入。已发工资禁止新增或撤销该月份奖惩。
- 工资表单的奖金/扣款为只读汇总，奖惩不在工资表单录入。工资卡片及员工 App 分列奖励、处罚扣款和押金扣款，并显示原因；员工工资单包含处罚/押金/其他扣款细分，避免误把押金当处罚。
- 手动工资表单选择员工/月即加载押金及奖惩，不必点击自动计算。后端也检查并补入遗漏计划。修改已有计划时避免再加一次；计算月份早于押金开始月份时不扣。
- 原有待发工资缺少押金计划时，列表显示“应扣押金（待确认）”及提示，并在保存前禁用发放；编辑核对保存后再发放。不会在 GET 请求中改写生产工资，也不会改已发历史金额。
- 保存工资不登记“已扣押金”；确认发放才在同一事务里登记，重复确认不重复扣除。薪资期锁协调工资保存、发放与独立奖惩写入。

验证：SQLite 295 / PostgreSQL 298 项实际 HTTP 请求检查；自动首月押金、原有缺计划工资复核、下一月不重复、开始月份边界；独立奖惩在工资前后添加、撤销、重试、金额总计、已发锁定、员工自身工资展示与授权。Chromium 实际界面新增奖惩、手动工资自动带入、不重复编辑、撤销更新工资、独立三项卡片和员工 App 联动通过；173 项安全 Jest、146 项 stoploss 及三端路由浏览器回归通过。全部交易写入仅使用隔离合成员工，不写真实财务记录。
