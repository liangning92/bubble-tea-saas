# Build and publication must be separate

Independent review found master merges push four Docker latest tags despite the Windows gate. Installed workflows confirm docker-publish.yml logs into GHCR and docker push -a runs on master push. Remove that automatic publication path. Keep all DBs, production services, credentials and account/security settings unchanged.

Learned from official GitHub REST workflow-runs/artifacts documentation (https://docs.github.com/en/rest/actions/workflow-runs and https://docs.github.com/en/rest/actions/artifacts), and read-only actual API responses: run path, head_sha, event, completed/success and artifact names/expiry can bind a release to a verified source and earlier run. Separate build-only workflows from manual-only publication workflows. Default publish=false; publication requires manual master invocation, explicit FULL source SHA already in master history, successful ordinary CI for that SHA, and an explicitly selected successful component verification run with the same SHA/path and all required unexpired artifacts.

Docker verification builds four existing Dockerfiles without registry login/push, saves locally verified images plus SHA/image-id/tar checksum manifests. Manual Docker publication loads those exact prior artifacts (does not rebuild), verifies their checksums, image IDs and revision labels, and pushes only full-SHA tags. It NEVER changes latest or branch tags. Thus build, merge and even immutable-image publication cannot silently advance a latest-following production device/container. Deployment/restart is a separate action outside these workflows.

Windows build stays on GitHub Windows and becomes artifact-only with no release/write job. Separate manual publication downloads the exact verified Windows artifact and checks installer/version/SHA512 plus compatibility and old-version-preservation evidence before creating any Release. ExistingDatabaseCompatible remains FALSE, so actual Windows publication is still blocked pending authorized legacy compatibility clearance. No real migration is enabled. New publication workflows need registration on master before they can be manually invoked; a merge itself cannot invoke them. This is release-source workflow code only, not a token/permission setting change or deployment.
