# Hermes operations runtime

Hermes handles free-form questions through the model. Incoming operational questions are not replaced by keyword categories. Backend-issued tools and actual stored receipts determine whether a business action happened; model prose is not a mutation receipt.

The existing Settings → AI → Agent panel owns the service switch, authorization expiry (including until revoked), execution timeout, and module read/write choices. Saving updates the installed Hermes grant, existing routes and delegated bindings atomically. A new permissions revision invalidates old executions. The historical October 2026 pilot cutoff no longer controls employee runtime authorization.

Inventory receipts/issues reuse the stock service, batch accounting and operation idempotency. Hygiene supports evidence reads and pending task creation/assignment without inventing physical completion. Staff tools support the directory and existing-shift scheduling; marketing, leave operations and training retain the existing tools. Every business tool and returned field is checked against current authority and the real conversation audience, including custom employee roles. General advice remains available when an operation is unavailable.

Memory is stored durably in the backend, independently of the Hermes child process. Each execution loads relevant retained notes and verified operation experience. Personal notes follow the same employee across private conversations; channel notes stay in that audience; store-wide notes require explicit operator confirmation. Role-policy changes exclude previously scoped notes. Native global/file memories remain isolated so another deployment's private memories cannot enter employee conversations.

The model can retain sourced facts, preferences and lessons, and supersede its earlier notes when corrected. Learned notes start unconfirmed. The AI settings memory panel supports search, correction, confirmation, store-wide publication, reversible archival, restoration and immutable version history. Operator edits invalidate active contexts. Disabling memory stops recall; disabling learning stops new memory and experience writes. Neither memory nor past success grants a new business permission, substitutes for fresh stock data or changes model weights. Growth here means durable feedback and lessons applied to subsequent work, not unrestricted self-modification.

The photo-recognition switch controls whether authorized chat JPEG/PNG attachments reach the configured model as real image parts. The isolated custom-provider profile declares the reviewed MiniMax-M3.1-Flash native vision capability (https://agent.minimax.io/tools/m3.1-flash); images are never represented as a filename or pretend analysis. Image bytes are checked against their owner, exact message grant, store and current conversation, then resized without EXIF for bounded model input. Original evidence remains private. Altered bytes or substituted image parts are rejected.

For an ingredient photo and a stock-out request, Hermes matches the actual inventory catalog and package/unit configuration. It asks for an ambiguous item or missing quantity instead of guessing an opened package's remaining contents. Ordinary stock-out uses the native withdrawal purpose. The actual stock-out receipt retains submitter, agent, message and photo hashes. Inventory → Stock operations → Stock movements preserves its metrics and actions and adds a lazy-loaded photo-evidence viewer. Its authenticated endpoint requires inventory visibility and a committed same-store receipt; it cannot fetch arbitrary chat files. No physical stock is modified solely to test this UI in production.

The private gateway runs through `scripts/hermes_employee/serve_gateway.py --config <private-json>` using the installed pinned Hermes Python/source. `ops/agent-pilot/employee-gateway.plist.in` is the launchd template: run at login, restart after exit, independent of Terminal. API and the sole worker remain Docker-managed. Host power/network and Docker availability are still prerequisites; this does not make an offline Mac into a cloud service.

The service has no fixed authorization stop date. Backend execution tickets retain their absolute expiry and fresh checks. `/health` exposes only service/protocol readiness on the private listener; it does not prove a real model or business operation succeeded. Process termination interrupts children, persists uncertain admissions, and never silently replays them. Keep the previous image, private config and journal for rollback.

Verification uses disposable PostgreSQL under `scripts/with-docker-test.py`, the real pinned Hermes with a synthetic provider, gateway subprocess/HTTP tests, and service startup/stop/restart tests. Real model, employee-visible output and deployed desktop/tablet/mobile UI acceptance must be recorded separately in the release evidence under `output/hermes-background-20261026`; synthetic tests do not establish production acceptance.
