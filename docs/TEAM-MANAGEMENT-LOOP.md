# 门店管理闭环：开发验收与运行边界

本改动处于隔离开发和验收阶段。代码存在、模型连接成功、受控测试通过均不等于已在生产启用；本轮隔离验收不部署、不启动生产常驻进程、不发送真实员工消息或 Push。后续发布须使用固定候选的实际验证和独立复审记录，并由管理主线统一协调。

## 消息与行动

消息事务持久入队，工作流消费者按当前门店、频道成员、负责人、授权版本和数据版本再检查后处理。员工原文属于业务输入，不可作为权限指令。日常工作回复不要求逐条人工审稿；付款、奖惩、权限和库存写入不在执行范围。

行动以来源 job 稳定幂等保存。多人可补充同一事项，不能借补充消息任意改负责人、期限或验收要求。真人负责人安排他人必须能从实际原文或已持久老板决定中确认唯一当前成员姓名及明确肯定指派。模型不能自行选择接收人。

期限或证据要求不足时保留 `waiting_details`。明确本人承诺可以提供期限；今天/明天及 hari ini/besok 的明确时刻按真实门店时区和原消息日期规范化，不能解析或时区不可用就追问。`open` 表示事项待办，`awaiting_evidence` 表示已提交材料仍待真人验收；“好的”“完成了”不能代替实质证据。附件记录存在不表示系统看过附件。只有有证据、实际负责人核对标准后才可 `verified`；取消为 `cancelled`。

行动终态与其明确绑定的 `pending_action` 来源 jobs 在同一事务结案；其它行动和独立 `awaiting_owner` 决定仍保留。导出读取持久状态，记录负责人、期限、证据与跟进，不把 AI 草稿当已核实事实。

## 重启与送达不明

队列、行动、来源回执和提醒租约持久保存；相同 requestId 重放读回原结果。尚未派发的过期租约可以安全重新领取；派发开始后结果不明保留 `unknown`，不能盲目再发。`in_app` 仅证明站内提醒已经落库，`accepted` 仅表示员工在系统内明确提交了相关证据，不代表工作完成、设备收到通知或用户已读。未证送达不能当员工违约。

当前通知契约复用现有持久 outbox 和 API 的扫描投递，不要求新凭据或新通知进程。暂停/禁用策略在领取前及领取后均检查。状态恢复和实际启用由主线按固定版本验收；本文件不证明生产 worker 正在运行。

## 营业节点、SOP 和事实边界

上下文只读取已保存且当前成员有权访问的排班、班次和分配的卫生/SOP任务。排班不是出勤证明；班次起止不是门店营业时间；卫生任务时间不是通用开闭店标准。未配置开店、闭店、交班标准或没有已分配 SOP 时明确为未知/待配置，不把种子或默认规则当成门店已确认流程。

库存数据是系统快照，不等于现场实盘。采购到货状态不授权再次入库。当前闭环不核算利润，不证明手机送达，也没有证明 Dot/ChatGPT 自主唤醒或巡店。

## 可复查证据

- `output/team-management-actions/validation.json`、`pg-final.log`：真实临时 PostgreSQL 的15组行动持久化与并发/重启组合测试（新增指派修正之前）。
- `output/team-management-actions/owner-directive-validation.json`、`owner-directive-pg.log`：指派修正后2组增量，含12个对照场景；不冒充整套重跑。
- `output/team-management-actions/export-results.json`、`export-pg.log`：终态结案与 HTTP 导出必要增量；只有日志终态通过且清理确认后才可记为通过。
- `output/team-management-loop/`：主线真实 HTTP/临时数据库、受控模型响应测试。受控 provider 响应不是真模型质量、费用或秒级响应证明；最终结果以主线固定源码与对应报告为准。

所有上述测试使用合成人员和独立临时数据。真实员工文本处理、生产开启、真模型耗时和设备通知送达未由这些测试验收。
