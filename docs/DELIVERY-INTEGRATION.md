# 外卖平台接入设计

GrabFood、GoFood及ShopeeFood目前尚未获得API权限。先保留平台适配接口和后台接入状态入口，取得权限后逐个平台完成真实接入。此阶段不生成模拟订单，不自动接单，不开放支付或库存写入。

## 当前完成的接口

后台读取 `GET /api/delivery/platforms?storeId=...`，仅管理员和经理可访问。经理只能查询所属门店。响应包含各平台的 `not_connected` 状态、`API_ACCESS_PENDING` 原因及全部为false的能力标记，不返回密钥或凭据引用。

平台适配器位于 `server/src/services/delivery/PlatformAdapter.ts`。保留以下内部合同，均按门店上下文创建：

| 方法 | 后期职责 |
| --- | --- |
| fetchOrders | 按平台分页游标读取订单，转换为统一订单结构 |
| confirmOrder | 向平台确认接单及预计制作时间 |
| updateStatus | 回传制作、待取、取消等状态及原因 |
| syncMenu | 同步商品、规格、价格和可售状态 |
| verifyWebhook | 使用原始请求字节和请求头校验平台回调 |
| parseWebhook | 将已经验证的回调转换为统一事件 |

当前所有操作抛出 `DELIVERY_PLATFORM_NOT_CONNECTED`，不会返回虚假的成功结果或用空列表冒充成功拉取。平台ID沿用现有 `grabfood`、`gofood`、`shopee`；其中shopee代表ShopeeFood。堂食direct不作为外卖API适配器。

平台订单结构分别保留商品金额、顾客配送费、平台费用及顾客支付金额，币种为IDR。顾客支付额与商户结算额不能混用；平台字段和金额含义必须以取得权限后的官方文档核实。该合同不是三家平台的HTTP协议，不预设其URL、鉴权方式或回调字段。

## 后续处理链路

平台回调或拉单 → 对应适配器 → 回调签名校验与事件转换 → 门店和商品规格映射 → 持久化外卖订单 → 经营系统订单及制作流程 → 状态回传 → 平台结算对账。

平台凭据只保存在服务端的密钥管理中，以引用传入适配器。每个平台店铺ID必须绑定本系统门店；不得直接相信回调提供的本系统storeId。原始回调在日志中应裁剪个人资料和密钥。

## 取得API后的实施步骤

1. 核实平台正式及测试环境、申请权限、鉴权刷新、限流、分页和订单状态定义，分别实现适配器；未通过验证的平台继续保持禁用。
2. 建立平台店铺与门店、商品与规格的映射。缺少映射的订单进入待处理列表，禁止静默替换商品或直接扣库存。
3. 用独立订单和事件模型持久化，约束平台、平台店铺、平台订单ID及事件ID的唯一性。现有DeliveryService的Config存储属于旧骨架，ID与Config记录ID、日期筛选等需重新核对，不能直接投入正式平台接入。
4. 实现幂等的事件接收、乱序及重复回调处理、状态迁移和失败重试。回调必须先验签、校验店铺绑定，再持久化；不能只凭订单号更新其他门店订单。
5. 单独实现外卖订单导入经营订单的事务和库存策略，保证同一订单只创建及扣减一次。先确定接单、付款、取消和退款各阶段对库存、收入、现金及积分的影响，再接入KDS和打印。
6. 状态回传采用持久化任务及退避重试；仅平台确认成功后展示回传成功。超时或结果不明时保留待核对状态。
7. 明确顾客实付、补贴、折扣、平台佣金、配送费、退款和商户净结算的对账关系。获得测试权限后验证这些金额，再提供正式账单导入或结算接口。
8. 平台测试通过后按门店启用，补齐状态和失败处理界面，再替换当前“尚未接入”页面为真实订单收件箱。

## 预留的HTTP入口

目前只实现只读状态接口。订单列表、接单、状态回传、菜单同步及平台回调的HTTP入口在取得平台文档后确定。建议路径为 `/api/delivery/orders`、`/api/delivery/orders/:id/accept`、`/api/delivery/orders/:id/status`、`/api/delivery/platforms/:platform/menu` 及 `/api/delivery/webhooks/:platform`。

这些路径尚未开放，也没有加入认证白名单。回调路由上线时需接入原始请求体读取和平台专属验签；不能复用管理员登录凭据，也不能仅因为“平台回调”就免除真实性校验。

## 本阶段验收

三平台状态为尚未接入；所有适配操作明确拒绝；后台不展示或生成虚构订单，不显示演示收入；状态接口拒绝匿名、收银员及经理跨店查询。API权限取得前，可以完成布局与合同设计，但真实订单、打印、库存及平台结算验收仍需后续接入。

本轮验证通过：后端及后台构建、后台翻译检查、125项专项测试；中英印尼三种语言的真实React页面检查均验证了三平台未接入状态、没有演示订单和加载失败可见提示。测试使用隔离账户及接口数据，没有向正式服务写入数据。这是源码及界面验证，不代表正式平台已接入或当前线上界面已更新。
