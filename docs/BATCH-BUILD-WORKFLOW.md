# 修改完成后自动检查、构建和发布

## 默认授权

用户于 2026-10-14 要求“修改发布规则，修改后自动发布”。该要求替代此前集中汇总后逐次确认的规则。智能体完成用户要求的修改后，自动完成适用检查、提交推送、合并、构建、发布和部署，无需用户再次确认清单、SHA 或上线动作。

用户明确说“等待其他修复”“仅提交”“只构建”“不发布”时以这次指示为准。不要把其他未完成任务自动混入本次发布。

## 执行流程

1. 在当前任务的干净分支完成修改，只提交该任务文件。
2. 读取实际线上组件的源码 SHA，以实际发布版本为基准，核对主分支和其他已上线修复，生成完整目标 SHA 的差异清单。Windows 和各 Docker 组件基准可能不同，分别记录。
3. 使用 scripts/batch-build-report.cjs 生成报告，运行对应类型、翻译、回归和源码预检。报告是审计记录，不是等待人工确认的关卡。
4. 推送前读取 GitHub 当前触发器；推送并合并后固定完整目标 SHA，在该精确源码上自动调用 CI。CI 成功后自动调用相应组件构建。不要因移动分支改变已选目标。
5. 只发布同一目标 SHA 成功构建并验证过的产物。不要重新构建发布产物，不能复用其他 SHA 的成功结果。
6. 部署前重新读取线上 SHA。若它已变化，保留新上线的修改，自动重新生成目标和差异清单，执行新目标的适用检查、构建和发布；不再要求用户重新确认 SHA。
7. 只替换本次受影响的服务，保存回滚版本，核对上线后的版本、健康状态及相关功能，记录最终结果。

## GitHub 工作流调用

ci.yml、build-windows.yml、docker-publish.yml 继续使用 workflow_dispatch。智能体依照上述持续授权自动调用，保留精确源码和验证产物门禁；这不是等待人工在 GitHub 点击，也不是恢复每次推送全量构建。

- base_sha 是实际已核验的完整发布/比较基准，必须是目标祖先；reviewed_sha 是完整目标，必须等于该工作流的 github.sha。
- confirmed=true 表示此次执行符合用户的自动发布授权，不要求用户为每个目标 SHA 再发一次确认。
- 核对 run 的 head_sha 和实际执行的 verify 作业。全跳过、失败或错误 SHA 的运行不能用作发布证据。
- release-docker.yml 使用明确的受影响 services 或 auto，source_sha 和 verification_run_id 指向同一份成功验证的产物；Windows 同样保留源码、验证和安装器门禁。
- GitHub 当前触发器与本地规则分别核验；未提交到远端的工作流修改不能声称已经生效。

## 默认按改动范围检查

- scripts/ci-scope.cjs 根据完整基准到目标差异及真实导入消费者选择相关检查。改名和删除均纳入比较。缺失基准报错，不用全量检查代替。
- full_regression=false 为默认。仅用户明确要求全量时才设置 true；不能用无关收银、支付、打印或 Windows 历史回归作为后台小修改的发布前置。
- 产品图和产品分析修改运行对应后台类型、翻译、媒体/产品及页面检查。CI 可能检查真实依赖消费者，但不因此发布无关组件。
- Docker 仅构建受影响的 api、admin、pos、staff 镜像。后台/API 修改不构建 Windows POS；Windows 只对实际相关源码变化选择检查、构建和安装升级验证。
- 共享依赖、数据库或基础配置改动按实际影响扩大范围。未匹配回归的代码仍执行组件类型检查，并明确记录覆盖情况；不填充无关历史回归。
- 正式检查失败后修复并重试。无法解决时报告具体阻塞，禁止跳过门禁、声称未执行检查通过或回退其他已上线修复。

生成差异报告和检查范围（不构建）：

```sh
node scripts/batch-build-report.cjs --base <完整线上基准SHA> --target <完整目标SHA>
BASE_SHA=<完整线上基准SHA> HEAD_SHA=<完整目标SHA> node scripts/ci-scope.cjs
```

记录 CI、组件构建、镜像/安装器发布 run ID、完整 SHA、最终线上版本及回滚版本，供后续自动发布核对。

## 真实 Web 验证

按用户 2026-10-14 的要求，每次界面修复后必须进入实际 Web 页面验证，发布后再次检查同一用户流程。使用用户实际访问的地址、真实业务数据和实际保存结果；HTTP 200、镜像源码标签、静态资源存在、模拟数据浏览器检查仅为辅助证据，不能代替真实页面验证。

产品图片问题必须区分媒体库上传、产品图片关联保存和详情渲染。核对产品编辑页的已保存图片，保存后重新打开产品详情，确认图片真正加载，并检查切换、放大等本次涉及的操作。不要把只有媒体库素材却未关联到产品的情况误报为已显示，也不要擅自按文件名批量绑定不确定的素材。

保存带页面上下文的截图，在最终结果中给出验证证据。真实页面的登录或访问不可用时，报告具体阻塞和未完成的验证，不声称已完成 Web 验证。

## 功能修改后的 UI 设计检查

- 每次修改功能后，必须检查受影响页面的 UI 设计：信息层级、模块保留、控件对齐、间距、密度、文字长度，以及桌面、平板和手机布局。不能擅自删减已有指标或操作；调整前后核对功能清单。
- 使用真实业务数据完成相关用户操作，检查加载、空数据、错误和筛选状态，保存修改前后截图；上线后重复验证并保存截图。模拟测试仅作辅助，未完成真实验证时明确报告。
- 发布记录必须说明 UI 检查结果、响应式验证及保留的模块；按本次实际改动选择检查，不默认全量回归。
