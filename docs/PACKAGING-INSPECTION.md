# 包材日核查：默认关闭的最小后端闭环

本批仅开发与隔离验证，不部署、不创建生产许可、不启动生产消费者、不调用真实模型、不通知真实员工。无需数据库结构迁移；测试数据库会安装项目现有库存账本触发器，以验证原盘点服务。

## 数据与批准边界

管理员明确选择一个本店私聊频道（本人和一位员工）、最多 20 个 `category=packaging` 的库存项目，以及本店营业日日触发时点。员工必须在当前有效 V2 权限中同时获准 `inventory.read`、`inventory.count`。后台角色、用户与员工关系、门店、频道成员和权限均从数据库重新检查，不能由客户端角色或旧令牌授予。

快照仅包含项目名称、账本单位、账面数量、最低/安全库存、最近已批准且观察记录单位匹配的实盘、已批准/待收货采购的剩余数量与预计日期、账本版本和数据质量。没有成本、供应商、员工工资、顾客、订单或任意 SQL。包材领用数量不代表每日实际消耗；缺少/过期实盘及未知到货日期会明确标记。快照构建只做 SELECT，不调用有写入的预警刷新服务。

模型仅接收这份固定快照，返回严格的 `{summaryZh}` 摘要草稿；没有模型工具、回调、自由查询或业务执行器。指派人、复核人、任务、证据标准与时限由后端生成。复用现有 AI 版本、连接状态、应用内费用估算台账和结果不明保护；没有真实供应商账单或冻结金额的推断。读取既存加密凭据不会创建缺失的主密钥。隔离模型 mock 使用构造器注入，不提供生产 mock 开关。

日任务按 **门店 + 门店营业日 + 规则版本** 持久去重，存入现有 `Config/team.communication` 队列族 `workflow.inspection.job.*`。重启不重新提交同一日任务。状态包括 `queued`、`processing`、`awaiting_approval`、`published`、`completed`、`cancelled`、`blocked`、`uncertain`、`dismissed`。已认领任务租约为 120 秒；超时、处理中进程中断、结果格式不明等不会自动盲重试，也不自动释放可能已计费的预留。

模型输出只生成现有运营计划草稿，未批准时没有任务或员工提醒。管理员在原计划页面查看快照、勾选批准并提交备注；同一事务完成计划发布、唯一任务、来源关联与唯一提醒收件箱/待投递记录。提醒写入失败会回滚整次发布；相同请求重放不重复派发。发布前重新检查当前权限、许可与 AI 连接版本、频道受众、快照有效期及内容指纹；过期时限也拒绝发布。此来源草稿不能经旧导入接口去掉巡检约束。

模型准入前在同一频道锁下同时预留计划与任务名额；原手工导入、纪要建任务和计划发布也统计此持久预留，不能抢占最后一个名额。计划导入消费计划名额，任务名额持续保留至人工发布同事务消费；失败/结果不明/过期租约或关闭则释放不再使用的名额，保留费用风险和来源记录。50 个未归档计划/预留或 200 个原任务/预留已满时供应商调用为零。已终结或关闭的巡检计划和任务转入独立历史前缀，保留原 ID、成员/fromSeq 可见性、版本及 job 关联，释放原计划/任务窗口；原页面显示近 20 条巡检历史，旧 ID 仍可读取和导出，不能恢复写入。

员工接单后通过原任务卡创建唯一关联盘点，并在原盘点页填写和提交实盘；所有旧盘点写入入口也检查关联任务的指派人与有效状态。同店其他员工及其他管理员不能代填；复核仅限许可中的原管理员。员工提交全部实盘后仍需在私聊提交本人证据，再提交任务。主管退回任务会将尚未批准的关联盘点恢复为待填写。盘点数量调整仍需主管在原盘点接口**单独明确批准**；任务验收不会调用库存调整。只有盘点已批准，指定复核人才可完成任务。最后管理员保护、退款、扣料恢复、采购、工资和惩罚业务均未更改。

取消任务同事务关闭尚未批准的关联盘点；反向在原盘点页取消也同事务关闭任务、job 和提醒。取消不撤销已批准库存变化。原许可/复核人已失效时，另一位本店真实在职管理员可通过原盘点取消入口清理失效工作，审计记录实际备用管理员；有效许可仍只允许原指定主管取消，其他管理员始终不能代为批准库存。同一 dismiss 入口允许备用管理员清理失效草稿及已派发但原复核人/许可失效的工作，包括尚未创建盘点的 assigned/accepted 任务；任务、未批准盘点、job、提醒和历史归档同事务关闭，故障会整笔回滚。备用管理员不会因此加入私聊或得到证据读取/库存批准权限；有效工作仍只能由原指定主管关闭。

提醒复用员工工作台收件箱及现有投递器；投递与收件箱读取会检查巡检任务、当前许可/权限、频道和计划状态。撤权、移出频道、暂停、关闭后失效。暂停/恢复不会重复已投递的外部推送。生产推送、真实员工照片、真实供应商响应和生产操作均未验收。

## API 与显式消费者

所有路径均要求既有身份验证；没有公开定时触发或任意工具端点。

| 路径 | 用途 |
| --- | --- |
| `GET /api/team/packaging-inspection/policy` | 管理员读取默认关闭的许可 |
| `PUT /api/team/packaging-inspection/policy` | 明确同意后启停单店许可，版本冲突拒绝 |
| `GET /api/team/packaging-inspection/snapshot` | 管理员读取当前许可内的最小快照 |
| `GET /api/team/packaging-inspection/jobs` | 管理员读取最多近 400 个日任务、状态历史及 worker 心跳 |
| `POST /api/team/packaging-inspection/jobs/:jobId/dismiss` | 指定复核人关闭草稿或已派发工作；备用管理员仅可清理失效工作，保留实际身份审计 |
| `POST /api/team/channels/:id/tasks/:taskId/inspection-count` | 本人接单后创建/重取唯一关联盘点 |

启用许可的严格请求字段：`expectedVersion, enabled:true, consent:true, channelId, assigneeId, inventoryIds, hour, maxCountAgeDays, snapshotMaxAgeMinutes, acceptWithinHours, completeWithinHours, expectedAiConfigVersion, expectedAiCheckRevision`。复核人及操作用户取真实当前管理员，不能在请求中任命。停用仅接受 `{expectedVersion, enabled:false}`。本批没有新增配置导航或生产许可写入；后续启用需针对真实门店、员工及项目另行确认。

消费者为 `server/src/workers/packagingInspection.ts`，从不被 API 启动流程导入。未来获得启用授权后，使用既有服务环境并显式设置 `PACKAGING_INSPECTION_RUN=1` 和唯一 `PACKAGING_INSPECTION_STORE_ID`，运行 `node server/dist/workers/packagingInspection.js`。缺少任一标志即拒绝启动；不会跨店扫描。默认每 30 秒检查许可与当日日任务，在 `inspection.worker` 保存时间、状态计数和错误码。日志不含密钥、员工原文或供应商响应。向该进程 PID 发送 SIGTERM/SIGINT 会结束循环并断开数据库。禁用许可同时停止新任务；历史任务保留。

首版使用许可版本指纹：更改许可、指定人或受众会使旧任务失效，需人工关闭处理；不会偷偷换人或用新数据替换已审草稿。每个营业日仅一个规则版本任务；结果不明没有自动重试或重新计费按钮。暂停计划可恢复，已失效许可不自动迁移旧任务。状态计数为最近最多 400 条记录的观测窗口。

**关闭网页后消费者可以继续运行；这台 Mac 关机、休眠或 Docker/进程停止后不能继续。** 本批没有服务器迁移或高可用运行保证。

## 隔离验证与证据

使用 `python3 scripts/with-docker-test.py -- python3 scripts/test-team-communication.py --packaging-inspection`：一次性真实 PostgreSQL、仓库现有账本触发器、真实路由/身份验证/服务/事务，以及仅在测试构造器注入的模型 mock。临时数据库、子进程由 finally 清理。没有生产连接、真实模型调用、外部通知或供应商/VAPID 密钥创建。

最后一组不是静态函数检查：真实子进程在**零页面请求**下执行日队列、创建草稿和心跳；SIGTERM 退出后重启，确认日任务与 AI 请求 ID 不变且仅一次模型准入。随后经真实 HTTP 完成原计划批准 → 员工工作台提醒收件箱 → 本人接单与关联盘点 → 实盘提交和聊天证据 → 指定主管独立盘点批准 → 任务验收 → 提醒关闭。`http-results.json.workerEndToEnd` 保存各节点 ID 与验证边界。

14 组检查覆盖跨店与伪造角色/client 拒绝、当前授权撤销与旧 token、快照纯读/过期/改变、未批准零提醒、并发去重、发布与提醒事务回滚、同店其他员工代填拒绝、非指定主管批准拒绝、超时/中断不盲重试、结果返回后权限/数据变化阻断；复审后增加双向取消/归档/失效管理员清理、50 名额满时零模型调用、最后名额与手工导入并发争用，405 条终态历史不遮蔽待处理日任务、200 个普通任务满额时零模型准入、199 个普通任务时阻止手工纪要/计划抢占预留任务名额，以及已派发但无盘点的失效工作清理和故障回滚探针。待处理索引独立于近 400 条历史展示窗口，并与 job 状态同事务维护。

`packaging-inspection-browser-check.cjs` 使用真实 React 组件及合成客户端验证原审批快照卡、本人盘点按钮、其他员工不可创建及 390/768/1365 宽度无横向溢出。before 表示同组件未提供巡检元数据，after 为提供合成巡检数据；不是生产前后截图。图片及结果位于 `output/packaging-inspection/browser`。既有团队沟通和 AI 设置分别运行原回归；改动消费关系纳入精确提交的 scoped CI。
