# 上传图片自动压缩

本规则用于新上传到门店媒体库的图片，覆盖产品图库、电视素材，以及 `/api/upload/product`、`/api/upload/dualScreen` 兼容接口。所有入口均经过 `MediaService.saveMediaFiles`，调用同一个优化器；已有素材与引用不做批量迁移，数据库结构不变。

## 显示与编码

- 以 4K 显示为基准，静态图片超过 3840 像素长边时按比例缩小到最多 3840；横屏、竖屏都适用，不裁剪、不放大小图。
- JPEG 照片转为 WebP，质量 86，保留清晰度优先。PNG、透明素材及静态 GIF 使用无损 WebP，避免文字边缘或透明背景被有损编码破坏。尺寸缩小仍属于重采样，无损指编码环节。
- 保持 EXIF 对应的正确显示方向后，再移除附加元数据；编码输出转换为 sRGB。
- 不超过 80KiB 的小图及无需缩小的 WebP 保持原样，避免重复有损压缩。GIF/WebP 动图保留完整原文件，APNG 检查动画控制块后同样保留。高位深图片及带 HDR gain map 的图片保留原文件，避免转换为 8 位 WebP 时损失信息。
- 输出没有变小就保留原文件；未缩小尺寸的重编码至少减少 5% 才采用。只落盘一个最终文件，不额外保留原图副本或多分辨率副本。
- 视频、音频及非媒体库的凭证/附件不经过这条图片压缩链路。图片上传额度仍为每张 5MiB，优化发生在服务端接受上传之后；不是通过压缩绕过上传大小校验。

## 存储与可靠性

编码在数据库事务前完成，避免编码耗时占用数据库锁。单进程同时只允许一个原生编码任务；像素解析上限 64 百万像素，编码上限 20 秒。异常或不能取得空间收益时保留原文件，上传继续按现有规则处理。临时优化文件采用同目录原子替换，成功后记录实际 MIME、扩展名和落盘大小；数据库失败时清除对应文件与临时文件。

原生编码依赖 Sharp 0.35.5，服务端要求 Node.js >=20.9。锁文件包含 Linux x64 与 Windows x64 的预编译依赖，现有 Windows 打包规则已覆盖 `server/node_modules` 的解包目录。Windows 被明确选择构建时，服务端依赖变动会进入对应安装器检查；本次没有执行 Windows 构建。

## 验证

`node scripts/test-media-insights.cjs` 使用一次性 SQLite/上传目录，覆盖尺寸、照片质量、透明像素、动图、旋转、文件与数据库失败清理，及产品/媒体库/副屏入口的一致存储信息。测试中的 2560×1440 JPEG 照片从 2,070,931 字节压缩至 782,894 字节，减少 62%，分辨率保持不变；与输入解码结果的 PSNR 为 38.9dB。该结果仅代表测试样例，实际节省取决于内容及原始编码。

发布范围应包含 API 以及待发布的媒体上传 Nginx 修复。现有图片自动压缩不改变展示页面或 POS 客户端源码。暂不构建或发布，随其他已完成修复一并汇总确认。

编码与平台支持参考：[Sharp 输出选项](https://sharp.pixelplumbing.com/api-output/)、[尺寸调整](https://sharp.pixelplumbing.com/api-resize/)、[安装与平台支持](https://sharp.pixelplumbing.com/install/)。
